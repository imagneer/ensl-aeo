# 작업 지시서 — 예산/API 사고 즉시 이메일 알림 추가

배경: 2026-09-04에 Anthropic 크레딧이 -$0.04가 되어 API가 차단된 사고가 있었음(claude/budget-watch-log.md
2026-09-04 항목 참고). 코난이 그날 바로 대응해서 해결됐지만, 이 사고가 루아에게 실시간으로 보고되지
않고 열흘 뒤(9/14) 예산 점검 로그를 코드로 다시 파보다가 뒤늦게 발견됨. 루아 요청: "사고가 나면 바로
이메일로 보고되게 만들어줘."

## 왜 매주 점검만으로는 부족한가 (에일 판단, 참고용)
매주 자동 예산 점검은 스냅샷 방식이라, 발생했다가 다음 점검 전에 이미 해결된 사고는 놓친다. 진짜
"즉시" 보고를 원하면 사고가 발생하는 바로 그 순간에 앱 자체가 이메일을 보내야 한다.

## 사전 조건 (루아가 먼저 할 일 — 코난이 대신 못 함)
- **(2026-09-14 정정) 루아가 Resend 계정을 이미 다른 프로젝트에서 쓰고 있음 — 새로 가입할 필요 없음.**
  기존 Resend 대시보드에서 엔슬 AEO MVP 전용 API 키를 새로 하나 발급(계정 공유해도 키는 프로젝트별로
  분리 — 나중에 어느 프로젝트가 이메일을 몇 통 썼는지 구분하기 위함).
- 발급받은 키를 코난에게 전달 (코드에 직접 하드코딩하지 말고 Vercel 환경변수로 등록: 예)
  `RESEND_API_KEY`, `ALERT_EMAIL_TO=huieunp@gmail.com`).
- 기존 계정에 이미 인증된 발신 도메인이 있는지 루아에게 확인 — 있으면 그 도메인으로 발신자 설정
  (예: `alerts@<루아 도메인>`), 없으면 Resend 문서에서 도메인 인증 없이 개인 이메일로 보낼 수 있는
  방법(테스트용 발신 주소 등)이 있는지 코난이 확인.

## 할 일 (코난)
1. `lib/email-alert.ts` 신설 — Resend API를 호출하는 `sendIncidentAlert(subject, body)` 유틸리티.
   실패해도(이메일 발송 자체가 실패해도) 원래 크론 로직을 막지 않도록 반드시 try/catch로 감쌀 것
   (알림 기능 오류가 본 기능을 멈추면 안 됨).
2. 아래 지점에서 이 유틸리티를 호출하도록 연결:
   - 각 엔진 어댑터(OpenAI/Anthropic/Gemini/Perplexity/SerpApi)에서 API 호출이 인증/크레딧/한도
     관련 에러로 실패했을 때 (401, 403, 429, 또는 "insufficient", "credit", "quota", "rate limit"
     같은 문구가 에러 메시지에 포함된 경우). 각 엔진마다 에러 형식이 다를 수 있으니 실제 에러 페이로드
     확인 후 판별 로직 작성.
   - `lib/llm-config.ts`의 `MAX_LLM_CALLS_PER_RUN` 상한에 걸렸을 때 (이미 로그는 남기고 있음 —
     여기에 이메일 발송만 추가).
   - 각 크론 라우트(`aggregate-daily`, `check-alerts`, `collect-and-save`, `complete-diagnoses`,
     `compute-placement-narrative`)에서 처리되지 않은 예외로 크론 자체가 실패했을 때.
3. **중복 방지(쿨다운)**: 같은 종류의 사고(같은 플랫폼 + 같은 에러 유형)로 하루에 여러 번 이메일이
   가지 않도록 제한. 간단하게 Supabase에 `alert_log` 테이블(플랫폼, 에러유형, 마지막 발송 시각)을
   두고, 마지막 발송 후 예: 6시간 이내면 스킵하는 방식 추천 — 구체 구현은 코난 판단.
4. 이메일 본문에 최소한 포함할 것: 발생 시각(KST), 어느 플랫폼/크론에서 났는지, 에러 메시지 원문,
   "지금 자동으로 막힌 건지 계속 재시도 중인지" 상태.
5. 테스트: 실제 사고를 재현하긴 어려우니, 에러를 강제로 발생시키는 테스트 경로(예: `?simulateError=1`
   같은 쿼리 파라미터로 의도적으로 에러를 던지게 하는 임시 코드)로 이메일이 실제로 도착하는지 1회
   확인 후 그 테스트 코드는 제거.

## 하지 말 것
- 이메일 발송 로직이 예외를 던져서 원래 크론/API 응답을 막는 일이 없게 할 것(알림 기능 때문에 본
  기능이 죽으면 본말전도).
- API 키를 코드에 하드코딩하지 말 것 — 반드시 환경변수.

## 처리 결과 (2026-09-18, 코난)

**Resend 도메인 인증**: 이미 완료돼 있었음 — `oddfish.co.kr`가 Resend에 인증된 상태(9/8
확인, Provider: Vercel). 기존에 CLAUDE.md 기술부채에 적혀있던 "DNS 완전히 죽음" 상태는
그 사이 해결된 것으로 보임(네임서버가 카페24 → Vercel DNS로 이전됨, 정확한 시점은 미확인).
별도 가입 없이 루아가 기존 계정에서 프로젝트 전용 키를 발급해서 전달함(`RESEND_API_KEY`).
발신 주소: `alerts@oddfish.co.kr`.

**구현 내용**:
- `lib/email-alert.ts` 신설 — `sendIncidentAlert()`, 전부 try/catch로 감싸 절대 throw 안 함,
  키 없으면 조용히 스킵. 쿨다운(6시간, platform+errorType 조합별)은 신규 `alert_log` 테이블로 관리
- 에러 유형 분리: `auth_credit`(401/403/인증·크레딧) / `rate_limit`(429) / `llm_call_cap` /
  `unhandled_exception` — 401·429를 같은 유형으로 묶지 않음(재시도로 나아질 에러인지가 다름)
- 연결한 지점: `collector.ts`의 6개 엔진 최종 실패 지점(재시도까지 다 실패한 후, 어댑터마다
  따로 안 넣고 한 곳에서 판별) / `aggregator.ts`·`mention-feature-roles.ts`의
  `MAX_LLM_CALLS_PER_RUN` 상한 도달 시 / 5개 크론(`aggregate-daily`, `check-alerts`,
  `collect-and-save`, `complete-diagnoses`, `compute-placement-narrative`)의 처리되지 않은
  예외 발생 시

**테스트**: `?simulateError=1` 대신 임시 API 라우트(`app/api/test-incident-alert`)로
실제 Resend API에 1회 발송 → 루아 지메일 수신 확인 완료. 테스트 라우트는 삭제함.

**추가 발견 및 대응(작업지시서 범위 밖, 같은 날 확인된 사고)**: 9/11~13 KST에 "인지 질문"
수집 회차가 3일 연속 통째로 0건 저장되는 사고가 있었음(합계 약 250건 결측). Supabase
공식 상태 페이지 확인 결과 "Unresponsive Projects" 장애(9/10~9/12, Free/Nano 요금제
프로젝트가 몇 시간 뒤 응답을 멈추는 버그)와 시점·증상이 일치 — 우리 코드 버그가 아니라
인프라 쪽 문제로 추정(확정은 아님, Supabase가 우리 프로젝트를 콕 집어 확인해준 건 아님).
이번 작업지시서의 알림 인프라를 이 사고 대응에도 바로 활용: `collector.ts`의 인지/자리
회차 하나가 통째로 실패하면 15초 후 1회 자동 재시도 → 그래도 실패하면 즉시 이메일 발송하도록
