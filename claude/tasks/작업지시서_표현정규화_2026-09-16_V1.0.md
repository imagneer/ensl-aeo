# 작업지시서: 소개-추천 표현 정규화 (특징 TOP10 비교 로직)

**작성일**: 2026-09-16
**작성자**: 에일 (루아 검토 후 코난에게 전달)
**상태**: 설계 합의 완료 → 구현 대기
**관련 배경**: Day22 "간극→서사" 재설계, 2026-09-16 루아·노바 리뷰

## 왜 (배경)

"인지와 추천의 서사" 화면의 TOP10 비교(소개 특징 vs 추천 표현)에서, 초록색 하이라이트가 실제 개념 일치를 정확히 반영하지 못하는 문제가 발견됨.

**사실 확인됨 (스크린샷 원본 대조 완료)**:
- **과다 집계**: 왼쪽 "위치"(1위), "365일 연중무휴 진료"(4위)가 오른쪽에서 각각 복합 문구(1위: "화곡역 1분 거리에서 365일 진료")와 단독 문구(3위, 5위)로 쪼개져 두 자리씩 차지함 → 겹치는 실제 개념 수(2~3개)보다 하이라이트 개수(좌 3 / 우 4)가 부풀려 보임
- **과소 집계**: 오른쪽 4위 "일요일 진료"는 왼쪽 "365일 연중무휴 진료"와 같은 상위 개념(진료 시간)인데 지금은 하이라이트 안 됨

**아직 가설 (코드 확인 필요)**:
- 좌우 리스트가 서로 다른 추출 단위를 쓰고 있을 가능성 (왼쪽 = 답변 여러 개를 묶어 정리한 특징 / 오른쪽 = 답변 원문에 가까운 표현). 좌우 표기 단위가 다른 것(왼쪽 "7/7일" vs 오른쪽 "7%·16건")은 사실이지만, 이게 추출 로직 차이 때문인지는 미확인.

**연결되는 다른 작업**: 이 문제는 별도로 논의 중인 "소개-추천 공통 특징 1개를 히어로에 쓰자"는 계획의 선행 조건임. 정규화 없이 그 계획부터 실행하면 같은 이중 집계 버그를 그대로 상속함.

---

## 무엇을

1. TOP10끼리 순위로 비교하는 방식을 버리고, "소개에서 나타난 핵심 개념이 추천 답변 전체(220건)에서 얼마나 나타나는지"를 비교하는 방식으로 전환
2. 이를 위해 원문 표현을 원자 단위로 분해한 뒤 상위 개념으로 묶는 정규화 레이어 추가

---

## 어떻게

### 1단계 — 원인 확인 (코딩 전)
소개 특징(19개 후보)과 추천 표현 추출에 실제로 쓰인 프롬프트/로직을 코난이 확인해서, "좌우 추출 단위가 다르다"는 가설이 맞는지 먼저 확인. 맞다면 어느 쪽 기준으로 통일할지(원자 표현 기준 권장) 결정.

### 2단계 — 카테고리 가설 검증
노바가 제안한 5개 카테고리를 시작점(가설)으로 삼되, 눈에 보이는 20개 항목이 아니라 **특징 후보 19개 전체 + 추천 답변 원문 220건 전체**에 적용해서 검증:

- 지역·접근성 (강서구/화곡동/화곡역/화곡역 1분)
- 진료 시간 (365일/연중무휴/일요일 진료)
- 협진 (분과별 전문의/서울대 의료진/협진 체계)
- 임플란트 (전문성/고난도/전체 임플란트)
- 제작 시스템 (자체 기공실/보철물 제작)

검증 기준: 이 5개로 전체 데이터가 커버되는지, 커버 안 되는 항목이 몇 개나 나오는지, 하나의 원문 표현이 두 카테고리에 걸치는 경우는 어떻게 처리할지.

### 3단계 — 판정 로직
기존 파이프라인 재사용: Haiku 1차 카테고리 판정 → 애매한 경우(카테고리 간 걸치는 표현)만 Sonnet 재검수. `reason_stated` 판정 때와 같은 구조. 새 판정 규칙을 처음부터 만들지 않고 기존 구조를 확장하는 방향.

### 4단계 — 사람 검증
카테고리 매핑 결과도 기존 세 화면과 동일하게 사람 검증 큐 대상 (특히 새 브랜드에 처음 적용할 때는 필수). 카테고리로 묶더라도 각 항목은 항상 원본 답변 원문과 연결 유지.

### 5단계 — 화면 반영
TOP10 좌우 대조를 "카테고리별 소개 강도 vs 추천 등장 비율" 비교로 교체. 비율 표기 시 분모 항상 함께 표시.

## 1~2단계 조사 결과 (2026-09-16, 코난 — 실측 확인)

### 1단계: 좌우 추출 단위 차이 — **가설 확인됨**
- 왼쪽(소개 특징): `brand_expressions`(원자 표현) → `buildGroupingPrompt`([lib/brand-one-liner.ts:143](../../lib/brand-one-liner.ts:143))로 **LLM이 여러 원자 표현을 묶어 새로 요약한 라벨**을 만듦 → `brand_feature_candidates.feature_name`. 3단계 파이프라인.
- 오른쪽(추천 표현): mentions 원문 → 원자 표현 추출(`extractExpressionsFromParagraphs`) → **묶는 단계 없이** 문자열 그대로 빈도 카운트([lib/placement-narrative.ts:109](../../lib/placement-narrative.ts:109)). 2단계 파이프라인.
- 현재 겹침 판정 `markTop10Overlap`([lib/gap.ts:92](../../lib/gap.ts:92))는 부분 문자열 토큰 매칭 — 이 단위 차이를 못 메꿈.

### 2단계: 5개 카테고리 가설 — **실데이터 기준 커버리지 부족 확인, 기존 7개 카테고리로 통일 결정**
- 최신 진단(365서울원탑치과, 2026-09-01~07) 실측: 소개 특징 후보 **41개**(확정18/가능성있음8/관찰중15, 문서의 "19개"보다 많음 — 이후 데이터 누적으로 추정), 추천 표현 원문 세그먼트 **187건**(문서의 "220건"은 1차 진단 기준 수치, 진단 회차가 바뀌어 달라짐).
- **중요 발견**: `brand_feature_candidates.category`에 이미 7개 카테고리(치료분야/진료체계/의료역량/환자상황/이용편의성/지역_조건/일반적표현)가 있고, 41개 전부 이미 이 체계로 분류돼 있음.
- 노바 제안 5개 카테고리(지역·접근성/진료시간/협진/임플란트/제작시스템)를 키워드 매칭으로 대조: 왼쪽 확정(tier) 18개 중 약 7개(39%), 오른쪽 원문 187건 중 44건(24%)이 5개 밖(친절/응대 27%, 후기·평판·신뢰 17%, 통증·마취·진정법 16%, 가격·비용 11%, 사후관리 10% 등 패턴 있음).
- **루아 결정(2026-09-16 채팅)**: 5개 신설 안 함 → **기존 7개 카테고리로 통일**. 오른쪽도 7개로 분류하되 카테고리 일치만으로 동일 특징 판정 금지, 세부 의미 재판정 후 확신 낮은 것만 상위모델/사람검수. 7개 어디에도 안 맞는 사례는 '일반적표현'으로 뭉개지 말고 별도 기록(반복되면 카테고리 보완 검토).

### 조사 중 발견한 기존 패턴과의 차이 (설계 시 참고)
- 프로젝트에 "Haiku 1차 → 확신 낮으면 Sonnet 재검수"라는 **수치/조건부 분기 패턴은 기존에 없음**. 실제 두 변형: (1) `reason_stated`(Haiku 판정→Sonnet **전건** 무조건 재검수, [lib/mention-feature-roles.ts:170](../../lib/mention-feature-roles.ts:170)), (2) 특징 후보 대립 탐지(Sonnet 탐지→Sonnet **전건** 무조건 재검수, boolean `confirmed`만 사용, [lib/brand-one-liner.ts:787](../../lib/brand-one-liner.ts:787)). 확신도는 전부 텍스트 지침이거나 enum(`high/medium/low`, `confirmed/estimated/...`)이지 숫자 점수가 아님([lib/badge-thresholds.ts], [lib/citation-linker.ts], [lib/trend.ts]).
- 사람 검수 큐(`review_items`)는 현재 "해석·제안 층" 문장(brand_one_liner 등)만 대상이고, `feature_conflict_summary` 타입이 Sonnet 2단계 판정 결과를 큐에 넣는 유일한 선례(`lib/brand-one-liner.ts:1042`).
- 이번 기능(카테고리+세부매칭+확신 분기)은 이 선례들을 참고하되 **새로 설계해야 하는 패턴**임 — 순수 재사용이 아님.

임시 프로브 라우트(`app/api/probe-category-validation/route.ts`)로 조회, 확인 후 삭제함.
