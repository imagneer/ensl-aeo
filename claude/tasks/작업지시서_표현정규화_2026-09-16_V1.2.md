## 왜 (배경)

"인지와 추천의 서사" 화면의 TOP10 비교(소개 특징 vs 추천 표현)에서, 초록색 하이라이트가 실제 개념 일치를 정확히 반영하지 못하는 문제가 발견됨.

**사실 확인됨 (스크린샷 원본 대조 완료)**:
- **과다 집계**: 왼쪽 "위치"(1위), "365일 연중무휴 진료"(4위)가 오른쪽에서 각각 복합 문구(1위: "화곡역 1분 거리에서 365일 진료")와 단독 문구(3위, 5위)로 쪼개져 두 자리씩 차지함 → 겹치는 실제 개념 수(2~3개)보다 하이라이트 개수(좌 3 / 우 4)가 부풀려 보임
- **과소 집계**: 오른쪽 4위 "일요일 진료"는 왼쪽 "365일 연중무휴 진료"와 같은 상위 개념(진료 시간)인데 지금은 하이라이트 안 됨

**확인 완료 (코난 코드 확인, 2026-09-16)**:
- 왼쪽 '소개 특징'(19개로 알았으나 실제 41개 — 아래 정정): `brand_expressions`(원자표현) → `buildGroupingPrompt`(lib/brand-one-liner.ts:143)로 LLM이 새 요약 라벨을 붙인 **가공 후** 결과
- 오른쪽 '추천 표현': `mentions` 원문 → 원자표현 추출 → 묶는 단계 없이 문자열 그대로 빈도 카운트(lib/placement-narrative.ts:109), **가공 전** 결과
- "서로 다른 기준"이 아니라 "서로 다른 처리 단계"를 비교하고 있었던 것 — 확정된 사실

**연결되는 다른 작업**: 이 문제는 별도로 논의 중인 "소개-추천 공통 특징 1개를 히어로에 쓰자"는 계획의 선행 조건임. 정규화 없이 그 계획부터 실행하면 같은 이중 집계 버그를 그대로 상속함.

## 어떻게

### 1단계 — 원인 확인 ✅ 완료 (코난, 2026-09-16)
두 가정 모두 코드로 확인됨:
1. 왼쪽 = `brand-one-liner.ts:143` LLM 그룹핑 결과 (가공 후)
2. 오른쪽 = `placement-narrative.ts:109` 원문 빈도 집계, 그룹핑 단계 없음 (가공 전)

재조사 불필요. 2단계로 진행.

### 2단계 — 정규화 방식: 기존 7개 카테고리(1차) + 카테고리 내 세부 매칭(2차)

루아가 채팅으로 준 지시(`brand_feature_candidates.category`: 치료분야/진료체계/의료역량/환자상황/이용편의성/지역_조건/일반적표현, 총 7개)와 V1.1의 "41개 클러스터 매칭" 방식이 서로 다른 세밀도라 충돌했음. 대체가 아니라 상위/하위 레이어로 합쳐서 반영:

**1차 — 카테고리 정규화 (양쪽 다 기존 7개로 통일)**
- 소개 특징(41개)과 추천 표현(220건에서 뽑은 원자표현) 모두를 기존 7개 카테고리에 분류
- 7개 중 안 맞는 표현은 "기타"로 뭉개지 말고 별도 기록만 (루아 지시). 반복되면 그때 카테고리 보완 검토
- 효과: "가공 후 vs 가공 전" 비대칭이 카테고리 레벨에서는 사라짐 — 새 타당성 검증 없는 분류를 새로 설계할 필요도 없음(기존 스키마 재사용)

**2차 — 카테고리 안에서 세부 개념 매칭 (같은 카테고리로 묶인 것끼리만)**
- 7개 카테고리는 너무 넓어서(예: "365일 진료"·"일요일 진료"·"분과별 협진"이 전부 "진료체계"에 같이 묶일 수 있음), 이것만으로 화면에 쓰면 "구체적으로 어떤 특징이 넘어갔는지"가 안 보임 — 이게 원래 이 화면을 다시 만든 이유(Day22, 요약보다 원문 우선)와 부딪힘
- 그래서 카테고리 정규화는 상위 집계·커버리지 확인용으로 쓰고, 화면에 보여줄 "구체적으로 어떤 표현이 겹치는지"는 같은 카테고리로 묶인 표현들끼리만 왼쪽 41개 클러스터 이름에 매칭 (범위가 좁아져서 문맥 오매칭 위험도 줄어듦)

**복합 표현 처리 규칙 (예: "화곡역 1분 거리에서 365일 진료")**
- 카테고리 분류 전에 원자 단위로 먼저 쪼갠 뒤 각각 분류 (지역_조건 + 진료체계 두 곳에 나눠 집계) — 하나로 억지로 합치면 정보 손실

**코난 확인 필요**
- `mentions`(추천 표현) 쪽에 `category` 필드가 이미 채워져 있는지, 아니면 이번에 새로 분류 로직을 붙여야 하는지

### 3단계 — 판정 로직
**정정**: `reason_stated`는 "애매한 것만 재검수"가 아니라, Haiku가 판정한 걸 예외 없이 전부 Sonnet이 재검수하는 구조(mention-feature-roles.ts:170, 조건부 분기 없음) — 이전 버전(V1.1)에서 잘못 적었음. 내가 실제 코드를 안 보고 "재사용 가능한 기존 패턴"이라고 추측으로 단정한 부분이라 정정함.

그러니 이 작업의 판정 로직은 재사용이 아니라 신규 설계임. 우선 `reason_stated`와 동일하게 **Haiku 판정 → 전부 Sonnet 재검수**(조건부 분기 없이)로 시작하고, 실제로 돌려보고 비용·정확도를 본 뒤 조건부 분기 도입 여부를 다시 결정.

### 4단계 — 사람 검증
카테고리 매핑 결과도 기존 세 화면과 동일하게 사람 검증 큐 대상 (특히 새 브랜드에 처음 적용할 때는 필수). 카테고리로 묶더라도 각 항목은 항상 원본 답변 원문과 연결 유지.

### 5단계 — 화면 반영
TOP10 좌우 대조를 "카테고리별 소개 강도 vs 추천 등장 비율" 비교로 교체. 비율 표기 시 분모 항상 함께 표시.

## 코난 확인 결과 (2026-09-16)

**1. `mentions`(추천 표현) 쪽에 `category` 필드가 이미 있는지 → 없음, 신규 구현 필요.**
`PlacementNarrativeTop10Item`([lib/supabase.ts:3405](../../lib/supabase.ts:3405))은 `{keyword, count, rate}` 세 필드뿐. `mention_feature_roles` 테이블(`docs/day22-mentionfeatureroles-schema.sql`)에도 category 컬럼 없음. `category`(`FeatureCategory` enum)는 오직 `brand_feature_candidates`(왼쪽 전용)에만 존재함 — grep 0건으로 재확인.

**2. 41개 클러스터가 7개 카테고리에 고르게 퍼져 있는지 → 아니오, 편중돼 있음.**
의료역량 13 / 이용편의성 9 / 일반적표현 7 / 환자상황 4 / 치료분야 4 / 지역_조건 2 / 진료체계 2 (합계 41). 지역_조건·진료체계처럼 항목이 2개뿐인 카테고리는 2차 세부 매칭(카테고리 내 클러스터 매칭)의 변별력이 크지 않을 수 있음 — 구현 시 고려 필요.

**3. 복합 표현("화곡역 1분 거리에서 365일 진료")을 원자 단위로 쪼개는 로직이 이미 있는지 → 없음, 신규 구현 필요.**
`buildExtractionPrompt`([lib/keyword-extractor.ts:112](../../lib/keyword-extractor.ts:112)) 규칙 2 "표현은 짧은 어구로 뽑아라, 문장 전체를 통째로 뽑지 마라"는 **길이** 제약일 뿐 **개념 분리** 지시가 없음. 실제로 이 복합 표현이 하나로 뽑힌 사례가 이미 실측(스크린샷 대조)으로 확인돼 본 문서 15행에 기록돼 있고, `lib/gap.ts:84`에도 같은 문구가 부분매칭 예시로 인용돼 있어 실데이터에 실존함이 재확인됨. `atomic|분해|decompose` 계열 후처리 로직은 `lib/` 전체에 없음(grep 0건) — 새로 만들어야 함.

임시 조사(Explore 에이전트, 코드 읽기만 수행, 파일 변경 없음)로 확인. 위 세 항목 모두 확정된 사실.
