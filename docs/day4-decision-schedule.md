## 확정된 결정

**하루 3시간대 × 2회 반복**으로 변경.

| 시각 | batch_id | run_index | 역할 |
|---|---|---|---|
| 09:00 | batch-1 | 1, 2 | 아침 수집 |
| 13:00 | batch-2 | 1, 2 | 점심 수집 |
| 18:00 | batch-3 | 1, 2 | 저녁 수집 |
| 00:30 (다음날) | — | — | 전날치 집계 → aggregated_metrics 1줄 생성 |

일일 호출 총량: 쿼리 5개 × 엔진 6개(구글AI/네이버AI브리핑/ChatGPT/Gemini/Claude/Perplexity)

> 참고: 이 문서 최초 작성 시점엔 엔진 5개(150회/일) 기준이었으나, 이후 세션에서
> 네이버 AI브리핑을 6번째 엔진으로 추가하기로 확정하면서 180회/일로 갱신됨
> (`ensl-aeo-mvp-schema-patch-naver.sql` 참고).

## 왜 이렇게 바꿨나

- **원안 문제**: 2시간대 × 3회는 같은 시각에 3번 몰아 물어보는 구조라, 사실상
  하루 안에서 "서로 다른 시점"은 2개뿐이었음(09시 컨디션, 18시 컨디션을
  각각 3중으로 확인하는 셈).
- **변경 이유**: API 호출 총량(따라서 비용)을 그대로 유지하면서, 배분만
  바꾸면(3시간대 × 2회) 하루 안에서 서로 다른 시점을 3개 확보할 수 있음.
- **알림 규칙과의 연결**: PRD의 "최소 3시점 이상 반복 확인" 알림 조건을
  하루 안에서도 자연스럽게 채울 수 있게 됨 (단, "3시점"의 정확한 정의는
  아래 미해결 항목 참고).

1. **snapshots 표**: `batch_id`는 하루 3개, 각 batch 내 `run_index`는 1~2만 사용.
2. **aggregated_metrics 표**: ~~집계는 하루 1회(00:30), 그날 하루치(3 batch × 2회 = 6개
   snapshots)를 묶어서 1줄 생성.~~
   **정정(2026-08-06, 노바 리뷰 반영):** 하루 1줄로만 집계하면 아침 100%/점심 0%/
   저녁 100% 같은 시간대별 차이가 일일 평균(66%)으로 뭉개져 사라짐. 그래서
   `aggregation_level` 컬럼(batch/daily)을 추가해 두 레벨을 분리:
   - **batch 레벨**: 배치(09/13/18시) 수집 직후 그 배치만(2회 반복) 즉시 집계 → 1줄
   - **daily 레벨**: 00:30에 그날 3개 batch(6개 snapshots) 전체를 묶어 집계 → 1줄
   `ensl-aeo-mvp-schema-patch-agg-level.sql` 참고.

3. **비용**: 하루 180회(엔진 6개 기준) → Tier 1(구글 AI Overviews + 네이버
   AI브리핑, SerpApi 담당)은 하루 60회 × 30일 = 월 1,800회로, SerpApi 월 5,000회
   플랜 범위 내(플랜 변경 불필요, 단 SerpApi가 엔진별로 크레딧을 다르게 매기지
   않는다는 전제이며 결제 전 대시보드에서 재확인 권장). Tier 2(OpenAI·Anthropic·

## Day 5 어댑터 개발 시 반드시 지킬 것

**엔진-티어 매핑표를 코드 한 곳에 고정할 것.** 하드코딩으로 여기저기 흩어놓지 말고,
아래처럼 단일 상수 파일(예: `lib/engine-config.ts`)로 관리:

```ts
export const ENGINE_CONFIG = {
  google_aio:         { tier: 1, label: '구글 AI Overviews' },
  naver_ai_briefing:  { tier: 1, label: '네이버 AI브리핑' },
  chatgpt:            { tier: 2, label: 'ChatGPT' },
  gemini:             { tier: 2, label: 'Gemini' },
  claude:             { tier: 2, label: 'Claude' },
  perplexity:         { tier: 2, label: 'Perplexity' },
} as const;
```

이유: `snapshots.engine_tier` 컬럼은 DB CHECK 제약으로 "1 또는 2"만 강제할 뿐,
"이 엔진명이면 반드시 이 tier"라는 자동 연결은 없음. 코드에서 실수로
`naver_ai_briefing`을 tier 2로 잘못 넣어도 DB가 안 막아줌. 위 상수 파일을
스냅샷 저장·집계·대시보드 표시 세 군데 모두에서 공통으로 참조하면 이런
실수를 원천 차단할 수 있음.

**정정 (2026-08-06):** 이전 버전에 "네이버 AI브리핑과 블랙키위 SEO 순위를 혼동하지
말 것"이라고 적었던 건 잘못된 내용 — 블랙키위는 이 프로젝트의 네이버 측정과
무관함. 실제 루아의 원래 수동 모니터링 시트("★365서울원탑치과 마케팅 모니터링")를
확인해보니, 네이버 쪽 측정은 블랙키위가 아니라 **네이버 통합검색 결과 페이지의
블록별 노출을 직접 눈으로 확인한 수동 기록**이었음(파워링크/플레이스/스마트블록/
인기카페글/추천키워드/인기글/브랜드콘텐츠 7개 블록, 시트 B~H열). 이 블록별 추적은
PRD상 여전히 MVP 스코프 밖(자동화 안 함, 수동 확인 영역으로 남음).

새로 추가한 네이버 AI브리핑은 이 7개 블록 중 어디에도 해당하지 않는 **완전히
새로운 측정 항목**이라, 기존 수동 기록과 혼동될 지표 자체가 없음. 오히려 루아의
원래 시트 구조(네이버 검색 블록 + 5개 AI 엔진을 한 화면에 나란히 배치)와 이번 MVP가
"네이버+AI 엔진을 함께 본다"는 점에서 더 닮아가는 방향으로 봐도 됨.

  - **관측 시점**(measurement point) = 하루 3회 (batch 레벨, 09/13/18시)
  - **알림 확인 시점**(alert threshold) = daily 레벨 기준 **3일 연속**

  `alerts.consecutive_periods`는 daily 레벨 aggregated_metrics만 기준으로 셀 것.
  batch 레벨의 일시적 흔들림(예: 점심 배치 한 번 0%)은 알림 판단에서 제외해야
  "단발 관측으로 결론 내지 않는다"는 원래 원칙과 맞음.
- ~~Vercel Cron 작업 개수(수집 3개 + 집계 1개 = 4개)가 Vercel Pro 플랜 한도 내인지~~
  **확인 완료(2026-08-06):** Vercel이 2026년 1월 20일부로 Cron Job 개수 제한을
  모든 플랜에서 프로젝트당 100개로 상향(기존 Hobby 2개/Pro 40개/Enterprise
  100개 구분 폐지). 4개는 한도 내에서 전혀 문제없음.

- **새로 발견한 주의사항 — UTC 변환 필수:** Vercel Cron은 타임존 옵션이 없고
  전부 UTC 기준으로만 스케줄을 등록함. 위 표의 시각(09:00/13:00/18:00/00:30)은
  한국시간(KST, UTC+9) 기준이므로, 실제 `vercel.json`에는 아래처럼 UTC로
  변환해서 넣어야 함:

  | 한국시간(KST) | UTC | cron 표현식 |
  |---|---|---|
  | 09:00 | 00:00 | `0 0 * * *` |
  | 13:00 | 04:00 | `0 4 * * *` |
  | 18:00 | 09:00 | `0 9 * * *` |
  | 00:30 (다음날) | 15:30 (전날) | `30 15 * * *` |

  Day 5~8에서 vercel.json 작성 시 KST 그대로 넣지 않도록 주의.
